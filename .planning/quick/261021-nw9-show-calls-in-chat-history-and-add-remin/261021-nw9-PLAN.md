<objective>
Implement the todo `.planning/todos/pending/2026-10-20-calls-and-reminders-in-chat.md`. It has two features that share one new chat element, a centred system line:

1. **Calls in chat history.** When a call ends, the server stores a "call" message, and both phones render it as a system line, with tap-to-call-back and missed-as-unread.
2. **Reminders.** Recurring and one-time reminders stored in SQLite and fired by an in-process scheduler, using web-push plus a system line in the chat. They are managed from Menu > Reminders.

Purpose: today calls leave no trace in the chat, and there is no way to remind yourself or each other.
Output:
- One drizzle migration: the message kinds "call" and "reminder" with their columns, plus a reminders table.
- Shared line/outcome/schedule helpers.
- Call-registry onEnded wiring.
- Reminder CRUD + scheduler + push.
- SystemLine and the Reminders UI.
- Server tests, and smoke scenarios in smoke-calls and smoke-chat.

Locked decisions honoured (confirmed 2026-10-21, see planning context):
- **Own reminders in chat.** Every fired reminder, including your own, produces a chat system line that both people see. This overrides the reminders note's "own ones notification-only". Pushes go only to the targeted person or people.
- **Calls exactly as in the calls note.** The server inserts the call message at call end. The line is centred, not a bubble. The outcomes are as listed above. Tap calls back with the same kind. A missed call is highlighted and counts as unread. A glare merge gives one line.
- **Reminders as in the reminders note.** Two types:
  - Recurring: every N min/h inside an active window, optional weekdays, pausable.
  - One-off: date/time, optional 15 min / 1 h heads-up, optional daily/weekly repeat.

  Reminders target me, the other person, or both. They live in a SQLite table with a ~30 s in-process scheduler and go out through the existing web-push sender. After downtime they fire late only within a few minutes. When push is suppressed they show in the app. All times are IST. They are managed from a ⋮ menu "Reminders" item with a list, toggles and an add/edit form, using preset components only. There are no Snooze/Done notification buttons.
- Speed first. Do the simplest thing that works and add no npm package.

Claude's discretion choices (documented here so the executor does not re-decide):
- Ringing that ended because the callee's Accept failed (WR-08 "failed") gets the line "Couldn't connect", which reuses the existing call-screen wording. A ring abandoned by a caller reload (WR-09 "dropped" while ringing) gets no line, because the replacing invite gets its own.
- A call line is timestamped when the call ends. Its sender is the caller.
- System lines use a Phosphor icon (PhoneIcon / VideoCameraIcon / AlarmIcon) plus text and a short time suffix. Toasts and pushes are text-only, so they use the "⏰" emoji.
- Heads-up firings also produce a line ("Meeting · in 15 min · …"), so every firing takes one code path.
- **Reminders are shared, like profile photos.** Both people see every reminder and either can edit, toggle or delete any of them. The creator stays the "from" person. "For" is stored as an absolute user id, or null for both.
- **The reminder title goes in the reminder push.** A reminder is useless without its text, and the Web Push payload is encrypted to the device (RFC 8291). The 261015-vkv "type only, never text" rule stays in force for chat messages.
- **Guards.** The minimum interval is 5 minutes, there are at most 100 reminders in total, and reminder pushes use TTL 300 s, so a stale reminder is not delivered hours later.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/reminders | untrusted reminder bodies (title, rule, target) from either logged-in person |
| browser → /api/messages, /api/messages/:seq/reaction | a client could try to forge, reply to or react to system lines |
| /ws call frames → call registry → chat DB | call ends now write messages; registry errors must not leak into call handling |
| server → push services (Apple/FCM) | reminder pushes now carry user-written text (encrypted Web Push payload) |
| push payload → service worker | sw.js must not take URLs or tags from the payload |

| T-nw9-01 | Spoofing | POST /api/messages | medium | mitigate | SendMessageBody stays strict (no kind or call fields). Only insertCallMessage and insertReminderMessage, which are server-internal, write kinds call and reminder. call-line.test asserts that the lines come only from call ends. |
