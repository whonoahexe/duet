Facts observed at planning time (2026-10-21, HEAD f26d08e):
- Media at rest is DUETENC (QT-4qu). Every stored file goes through encryptFile and is read through decryptToFile, readEncHeader and decryptChunks (server/src/media/crypto.ts). sharp runs only on plaintext inside media/work/<id>-XXXXXX scratch dirs (workRoot and attachmentDir in process.ts; the mkdtemp pattern is in uploads.ts complete() and process.ts runInScratch). Any new stored variant MUST follow that pattern (T-4qu-01).
- GET /media/:id/:variant (routes.ts) serves only names in its VARIANTS map. It requires a session, attachments.status = "ready" and an existing file, and it caches with private, immutable. Because a new photo is a new attachment id, the URL changes on every photo change, so immutable caching stays correct.
- processImage writes display.webp (long edge 2048, autorotated, no EXIF, HEIC already converted through heif-convert) and thumb.webp (640). A video's tile image is poster.jpg. Uploads are the chunked flow in web/lib/chat/upload.ts uploadFile(file, kind, onProgress), which returns an AttachmentDto that is usually still "processing".
- Users: the users table has no photo column. GET /api/users is public (the login tiles), and server/test/users.test.ts asserts its keys are exactly [displayName, id, username], so photoId must NOT be added there. GET /api/me is in server/src/auth/routes.ts. Its peer uses the `summary` projection, and the user comes from request.user, which has no photoId. server/test/auth.test.ts asserts /api/me with toEqual, so it needs `photoId: null` added.
